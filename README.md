# Erebor

Pulls new items from Fellow, Linear and other work sources into an Obsidian
vault using `claude -p`. Each run writes one note per meeting or ticket, then
updates the notes that link every decision, constraint and open question back
to its source: topic notes for each project, and area and people notes for what
stays true after a project ends. A generated index lets other Claude sessions
find all of it.

## Setup

Requires Python 3.10+, `git`, and Claude Code with the claude.ai connectors you
want to use already signed in (`/mcp`).

```sh
./run.sh                 # first time: creates config.json from the example
$EDITOR config.json      # set the vault path, sources, seed topics
./run.sh --init          # scaffold the vault (also runs automatically)
```

Keep the vault outside `~/Documents`, `~/Desktop` and `~/Downloads`. macOS
blocks launchd jobs from those folders, which matters once runs are scheduled.

## Running

```sh
./run.sh                       # all enabled sources, since each one's last run
./run.sh --source linear       # just one source (repeatable)
./run.sh --lookback 2          # ignore cursors, fetch the last 2 days
./run.sh --dry-run             # print the prompt and allowed tools only
./run.sh --index               # rebuild the vault's index, without a run
./run.sh --upkeep              # promote topics to areas and tidy, no sources
```

Exit codes: `0` ok, `2` partial (a source failed or was only partly fetched),
`1` failed, `75` another run holds the lock, `64` usage or config error.
`SIGTERM` or Ctrl-C cancels cleanly.

## How a run works

1. For each enabled source, the fetch window starts at that source's cursor
   minus one hour, capped at `max_lookback_days`. A first run uses
   `initial_lookback_days`.
1. `prompt.md` is rendered with those windows, the source instructions from
   `sources.json`, and your exclusions.
1. The index is rebuilt, so Claude starts from the notes as they are now.
1. Claude runs headless in the vault with `--permission-mode dontAsk`. It gets
   only the read tools listed for the enabled sources, plus `Edit` scoped to
   the vault, except `.claude/`, `.obsidian/`, `dashboards/` and `index/`.
   Anything else is denied.
1. Claude files both inboxes, captures every substantive item that involves
   you, and updates topics, areas and people.
1. If any topic holds decisions that aren't in the areas yet, a second,
   shorter Claude pass runs from `upkeep.md` with no source tools. It promotes
   up to five topics, archived ones first, and tidies part of what
   `index/lint.md` lists. Its cost is added to the run's.
1. After Claude exits, any DataviewJS block or inline `$=` query it wrote into
   a note is disabled, and the run is marked partial, because Obsidian would
   run them as code. The index is rebuilt again.
1. Claude writes `.state/run-result.json` with a status for each source. The
   runner merges it into `.state/last-run.json`, advances the cursor only for
   sources that succeeded, appends to `.state/history.jsonl`, and commits the
   vault. A source that reports an `error` keeps its cursor even when it is
   marked ok: the run is partial and the next one fetches that window again.

The vault's `.claude/CLAUDE.md`, hidden from Obsidian, defines the note
formats. It also guides interactive sessions: run `claude` in the vault and
ask questions about your projects.

## What the vault holds

- `sources/`: one note per meeting, ticket, PR or thread. Append-only.
- `topics/`: one note per project. These drive the In flight dashboard.
  Archiving a topic only takes it off the dashboard: its decisions still hold,
  stay in the index, and keep being promoted to areas.
- `areas/`: one note per system, product area or process, saying what is true
  now. The upkeep pass copies the lasting decisions and constraints of topics
  into their areas, five topics at a time.
- `people/`: one note per person: their role and what they own or decide.
- `index/`: generated by code from the notes above, never by Claude.

| File | Holds |
| --- | --- |
| `index/map.md` | Every area, topic and person in one line, with what it is tied to |
| `index/knowledge.md` | Every live fact, decision, constraint and question, one per line |
| `index/tickets.md` | Every ticket and PR, with the notes that mention it |
| `index/lint.md` | What needs tidying: unfiled notes, broken links, unknown names |

The index files link to every note, so they show up as hubs in Obsidian's
graph view; filter them out there with `-path:index`.

## Using the vault from other sessions

The `knowledge-vault` skill lets Claude sessions in any folder read the vault,
starting from its index. Its source is `skills/knowledge-vault/`. Install it,
and again after editing it, with:

```sh
./run.sh --install-skill
```

This writes the skill to `~/.claude/skills/` with the vault path from
`config.json`. If that folder is inside a git repo, the installed copy is added
to that repo's `.git/info/exclude`.

Then add allow rules to `~/.claude/settings.json`, using your vault path, so
sessions read the vault and append to its agent inbox without asking:

```json
{
  "permissions": {
    "allow": [
      "Read(~/Vaults/work/**)",
      "Edit(~/Vaults/work/agent-inbox.md)"
    ]
  }
}
```

Sessions write to the vault in two ways:

- `agent-inbox.md`, on their own. After using the vault a session appends what
  it used, what it couldn't find, what the code contradicted, and the links
  and facts it turned up. The next run files these under `sources/agent/` as a
  session's observations, which rank below a meeting or a ticket. Notes that
  sessions use together show up as related in `index/map.md`.
- `inbox.md`, with your yes. Action items, answers and decisions are recorded
  as yours, so the skill tells Claude to show you each line and wait.

Nothing blocks other sessions from changing the rest of the vault. The skill
tells Claude to suggest each change and wait for a yes before making it.

## Obsidian plugin (trial)

`plugin/` holds the same run as a local Obsidian plugin, written in
TypeScript. It works alongside the scripts. Both use the vault's `.state/`
folder, so each starts from the cursor the other left and neither starts while
the other holds the lock. The plugin reads `config.json`, the prompts and
`sources.json` from this checkout on every run, so the two can't drift apart.

```sh
cd plugin
npm install
npm run install-plugin   # build, then copy into the vault from config.json
```

Then turn on **Erebor** under Settings → Community plugins. After a
change to the plugin's code, run `npm run install-plugin` again, then turn the
plugin off and on.

| Command | Same as |
| --- | --- |
| Run ingest | `./run.sh` |
| Run ingest for one source | `./run.sh --source NAME`, with `--lookback DAYS` if you pick one |
| Run ingest with a lookback | `./run.sh --lookback DAYS` |
| Run upkeep | `./run.sh --upkeep` |
| Rebuild index | `./run.sh --index` |
| Cancel run | Ctrl-C |

The status bar shows the last run of either engine, and the tool a plugin run
is calling. A plugin run records `"engine": "plugin"` in
`.state/last-run.json` and `history.jsonl`; a script run has no `engine`
field.

While Obsidian is open, the plugin also keeps the index current between runs.
It rebuilds `index/` once after the vault opens, and about five seconds after
any note under `areas/`, `topics/`, `people/` or `sources/` changes, whether
you, a Claude session or a sync changed it. It waits while a run of either
engine holds the lock, because the run rebuilds the index as it ends. The next
run commits what changed. With Obsidian closed, the index is as fresh as the
last run or `./run.sh --index`.

- A run stops when Obsidian quits. Cursors only move on success, so the next
  run fetches the same window again.
- `--init`, `--install-skill` and `--dry-run` are script-only.
- The copy in the vault is a build of this repo, so installing adds it to the
  vault's `.git/info/exclude`.
- The bundle holds this checkout's path. Install again if the repo moves.

## Status file

`.state/last-run.json` is what a UI such as an Obsidian plugin reads:

```json
{
  "runId": "2026-11-02T160629",
  "status": "ok",
  "startedAt": "2026-11-03T00:06:29Z",
  "finishedAt": "2026-11-03T00:10:02Z",
  "error": null,
  "sources": {
    "linear": { "ok": true, "items_seen": 5, "notes_written": 5,
                "since": "2026-11-02T00:06:29Z" }
  },
  "topicsUpdated": [],
  "topicsProposed": ["checkout-redesign"],
  "areasUpdated": ["billing"],
  "summary": "Captured 5 checkout redesign issues…",
  "costUsd": 0.82,
  "tokens": { "input": 2468853, "cached": 2308862, "output": 19222 },
  "permissionDenials": 1,
  "upkeep": { "topics": ["billing-migration"], "ok": true },
  "lintEntries": 12,
  "logFile": ".../.state/logs/2026-11-02T160629.jsonl",
  "commit": "75efa8f"
}
```

`status` is `running` while a run is in progress, then `ok`, `partial` or
`failed`. Logs, the rendered prompt and stderr for each run are kept in
`.state/logs/` for 30 days.

## Adding a source

Add an entry to `sources.json` with its read-only tool names and instructions,
then enable it in `config.json`. Slack is listed but has no tools yet: connect
it with `/mcp`, list its tools, and add only the read and search ones.

## Development

```sh
python3 -m unittest discover tests
uvx ruff format . && uvx ruff check .
```

The end-to-end tests swap in `tests/fake_claude.py`, so they need no network.

The plugin has its own checks, which need Node 24 and `python3`:

```sh
cd plugin
npm test         # includes the parity tests
npm run check    # types
EREBOR_PARITY_VAULT=~/Vaults/work npm test   # also compare the index of a real vault
```

The parity tests run the script engine next to the plugin and compare what
they produce byte for byte: the index, both prompts and the Claude command.
They read the vault named by `EREBOR_PARITY_VAULT` and write nothing to it.
`plugin/src/python.ts` holds the places where Python and JavaScript treat text
differently; a change to the index code belongs in both engines.
